# ZeroPW 제품 정의와 의도 정렬

> 2026-09-12 사용자 교정: CLI·API 작업별 사전등록을 기본 UX로 삼는 제안은 거부됐다. 아래 본문은 2026-09-11의 이전 제안 기록이며 현행 구현 기준이 아니다. 환경·자격증명을 연결하고 기존 CLI를 사용하는 UX를 기준으로 재설계해야 한다. 이 교정은 비밀 노출 위험을 사용자가 수용했다는 뜻이 아니다.

> 같은 날 추가 확인: 실행 프로세스가 실제 값을 읽을 수 있다면 프로젝트 목적에 어긋난다는 사용자 지적이 있었다. 작업 사전등록 없는 UX와 에이전트가 제어하는 실행 코드에 원본 자격증명을 주지 않는 요구를 함께 유지한다. 일반 환경변수 주입만으로는 이 경계를 충족하지 못한다. 인증 중계·서명 위임과 지원할 CLI/프로토콜의 호환성을 검토하되, 모든 프로그램에 투명하게 적용된다고 가정하지 않는다.

작성일: 2026-09-11 · 제품 기획: Astra · 단계: 구현 전 제품 정의

## 1. 만들 제품

ZeroPW는 내가 가진 환경변수, API 키, 비밀번호를 클라우드에서 관리하고, AI 에이전트가 실제 값을 전달받지 않은 채 허용된 CLI·API 작업에 사용할 수 있게 하는 개인용 도구다. 에이전트는 “이 프로젝트의 개발 환경으로 연결을 확인해줘” 같은 작업을 요청하고, 신뢰된 실행기가 필요한 자격증명으로 실행한 뒤 제한된 결과만 돌려준다.

사용자는 비밀을 등록하고 사용 범위를 정한다. 에이전트는 어떤 연결과 작업을 사용할 수 있는지 알 수 있지만, 비밀을 조회하거나 복사하는 권한은 갖지 않는다. 반복되는 저위험 작업은 정해진 범위 안에서 자동 실행하고, 새 권한이나 영향이 큰 작업은 사용자가 승인한다.

제품의 출발점은 1Password의 개발자 기능이다. 직접 만드는 이유는 에이전트 작업에 맞는 사용 권한과 실행 경계를 소유하기 위해서다. 자체 개발이 구독보다 저렴하거나 더 안전하다는 가정은 하지 않는다. 클라우드 사용료, 유지보수, 복구 책임이 생긴다.

## 2. 사용자와 확인한 범위

- 첫 사용자는 제품 소유자 한 명이다. 환경변수·API 키·비밀번호와 CLI·API 사용에 집중한다.
- 제품의 저장소와 명령 실행기를 클라우드에 둔다.
- 제품을 개발하는 에이전트 하네스도 클라우드에서 운영한다.
- 기획·문서·PO는 Astra, 조사·구현·테스트 서브에이전트는 Sol, 적대적 검증은 Claude Opus가 담당한다.
- 지금 할 일은 제품 문서화와 의도 정렬이다. 현재 앱, Git 저장소, 배포 인프라는 없는 상태다.

다음 항목은 기획 제안이며 아직 사용자 확인 전이다. 명령 실행은 등록된 작업을 중심으로 제공한다. 클라우드는 개인 소유 계정의 단일 리전으로 시작하고, 초기 통합은 실제로 자주 쓰는 CLI 두 개 이하로 제한한다. 제공자, 예산, 리전, 첫 CLI는 구현 설계에서 확정한다.

## 3. 가장 중요한 제품 선택

“모델의 대화에 값을 쓰지 않는다”와 “에이전트가 값을 알아낼 수 없다”는 다른 요구다. 단순히 환경변수를 넣고 에이전트에게 자유로운 shell을 주면, 에이전트가 그 환경에서 실행하는 프로그램은 값을 읽을 수 있다. 출력 마스킹도 파일 저장, 인코딩, 네트워크 전송까지 막지는 못한다.

따라서 기본 경로는 등록된 작업 실행으로 제안한다. 예를 들어 `github.repository_status`나 `database.connection_check`를 제공하고, 실행 파일·인자 형식·대상·필요한 비밀·반환 항목을 작업별로 고정한다. 에이전트가 임의 shell, Python 코드, 플러그인, URL을 비밀과 함께 실행하도록 허용하지 않는다.

사용자가 원하는 자유도가 “어떤 CLI든 원하는 인자로 실행”에 가깝다면 별도 호환 모드가 필요하다. 이 모드에서는 실행 프로세스가 비밀을 읽을 수 있다는 조건을 받아들여야 한다. 이 선택은 제품의 보장 범위를 바꾸므로 첫 의도 정렬에서 확인한다. 초기 제안에는 호환 모드를 넣지 않는다. 추후 추가하더라도 고정 작업 모드와 프로젝트·연결·자격증명을 분리하고 동일 자격증명을 공유하지 않는다. 호환 실행에 사용한 값은 안전한 값으로 재분류하지 않으며 외부 발급처에서 폐기하고 새 값을 발급해야 한다.

보장 목표는 승인된 어댑터와 실행 경계 안에서 자격증명 원문을 모델 입력, 에이전트 작업 공간, 도구 응답에 전달하지 않는 것이다. 신뢰된 실행기와 필요한 외부 서비스는 값을 사용할 수 있다. 클라우드 관리자나 실행기 자체의 침해까지 막는 절대적 비노출 또는 zero-knowledge 제품이라고 표현하지 않는다.

보호 대상인 자격증명과 작업 결과 데이터도 구분한다. 사용자가 반환을 허용한 작업 결과는 모델과 모델 제공자에게 전달된다. 자격증명 비노출이 개인 데이터 전체의 비공개를 뜻하지 않는다. 자동 허용은 기본적으로 비어 있으며 사용자가 작업별 반환 항목과 데이터 민감도를 확인하고 켠다.

## 4. 사용 흐름

1. 사용자가 에이전트와 분리된 관리 화면에 로그인하고 프로젝트와 dev·staging·prod 환경을 만든다.
2. 값은 해당 화면에서 직접 입력하거나 `.env` 파일로 가져온다. 에이전트가 업로드 화면, 원본 파일, 요청 본문을 읽는 경로로 등록하지 않는다. 파일 가져오기는 데이터를 파싱하며 shell로 실행하지 않는다.
3. 사용자가 연결 대상과 사용 가능한 작업을 정한다. 예: 특정 저장소의 상태 읽기, 특정 개발 DB의 연결 확인. 저장된 참조만 프로젝트 설정에 둔다.
4. 에이전트는 native tool 또는 MCP로 작업 이름과 허용된 파라미터를 보낸다. 실제 비밀이나 범용 복호화 토큰은 받지 않는다.
5. ZeroPW가 호출자의 신원과 권한을 확인한다. 기존 정책 범위면 실행하고, 추가 승인이 필요하면 사용자 관리 화면으로 구체적인 실행 요청을 보낸다.
6. 신뢰된 실행기가 해당 작업에 필요한 값만 사용한다. 에이전트에는 성공 여부와 작업별 허용 데이터, 실행 ID만 반환한다.
7. 사용자는 사용 기록을 확인하고 연결 권한을 끊거나 키를 교체한다. 회수는 이미 외부 서비스에서 끝난 작업을 되돌리지 않는다.

사용 경험 예시: “개발 DB 연결 상태를 확인해줘” → 에이전트가 `database.connection_check` 요청 → 실행기가 고정된 연결 검사 수행 → `connected` 또는 사전에 정한 실패 코드 반환. 비밀번호와 원시 DB 오류 메시지는 대화에 나타나지 않는다.

## 5. 첫 버전의 기능

| 기능 | 첫 버전에 필요한 동작 |
| --- | --- |
| 비밀 관리 | 프로젝트·환경별 변수, API 키, 사용자명·비밀번호 묶음, 값 숨김, 변경·버전·비활성화 |
| 사용자 접근 | 강한 로그인과 재인증, 분리된 관리 세션, 복구 수단; 사람의 값 보기에도 단건 재인증·속도 제한·감사 적용, 일괄 export 제외 |
| 안전한 등록 | 직접 입력과 `.env` import, 미리보기는 이름·개수만 표시, 원문·요청 본문 로깅 금지 |
| 참조와 연결 | 값 대신 불투명한 연결 ID, 실행기가 소유한 비밀 매핑, 환경 간 권한 분리 |
| agent native tool | 사용할 작업 목록, 실행 요청, 상태 조회, 취소; 값 조회·내보내기 도구 없음 |
| 실행 정책 | 호출자·프로젝트·환경·대상·작업·만료·호출량·동시 실행 제한, 기본 거부 |
| 실행기 | 고정 어댑터, CLI 또는 HTTP 호출, 짧은 수명, 비밀을 갖는 작업과 agent 작업 공간 분리 |
| 결과와 기록 | 구조화된 결과, 원시 출력 차단, 값 없는 감사 기록, 실패·회수 이력 |
| 수명 관리 | 연결 권한 회수, 수동 키 교체와 버전 전환, 암호화 백업과 복구 점검 |

비밀번호는 초기에는 저장과 승인된 프로그램의 인증에 사용한다. 웹사이트 자동 로그인, TOTP, 패스키 보관, 카드·신분증 보관, 가족·팀 공유, 기업 SSO/SCIM, 다중 클라우드 동기화는 후속 범위다. SSH 서명과 단기 자격증명 자동 발급은 보안상 유용하지만 첫 사용처가 확인된 뒤 추가한다.

첫 검증용 작업 후보는 저장소 상태와 DB 연결 검사다. 저장소 응답은 예를 들어 `reachable`, `is_private`, `archived` 같은 불리언으로 한정하고 브랜치명·설명·커밋 메시지는 반환하지 않는다. DB 검사는 연결 결과 enum만 반환한다. 이 좁은 결과는 보안 경계를 검증하는 출발점이며, 풍부한 텍스트 결과가 필요한 작업은 데이터 노출 정책을 먼저 설계한다. 실제 첫 통합과 필요한 결과는 사용자의 반복 작업에 맞춰 선택한다. 배포·삭제·결제 같은 쓰기 작업은 인증 성공 여부와 별도로 작업 권한과 승인 규칙이 필요하다.

ZeroPW 자신의 인프라·KMS·비밀 저장소·감사·백업·DNS·복구·결제를 관리하는 자격증명과 하네스의 모델 계정 관리·호출 자격은 이 제품의 작업용 연결 대상에서 제외한다. 이들은 별도의 운영 관리 체계에 둔다. 사용자의 다른 프로젝트에서 사용하는 API 키는 관리할 수 있지만, ZeroPW의 통제 경계를 변경할 권한이 없어야 한다. API 사용에 따른 비용과 호출량도 해당 연결 정책에 포함한다.

## 6. 1Password에서 참고할 기능

1Password는 일반적인 로그인 정보 관리와 함께 개발자를 위한 환경변수 관리, CLI, SDK, 서비스 계정, SSH 기능을 제공한다. 아래는 전체 기능 목록이 아니라 ZeroPW의 요구에 직접 관련된 기능을 선별한 것이다. 조사 시점은 2026-09-11이며 각 제품 기능의 현재 조건은 링크에서 확인한다.

| 관련 기능 | 확인한 동작과 ZeroPW 반영 |
| --- | --- |
| Environments | 프로젝트·단계별 변수와 `.env` import를 지원한다. ZeroPW도 이 관리 단위를 채택한다. [S1] |
| secret reference와 `op run` | 참조를 실제 값으로 바꿔 자식 프로세스 환경에 주입하며 stdout/stderr에 나온 해당 값은 기본적으로 가린다. 마스킹 해제가 가능하고 변형·파일·네트워크 유출 방지는 별개다. ZeroPW는 고정 작업으로 제한한다. [S2] |
| 1Password MCP Server | Environment 관리용 서버는 매 동작 승인을 요구하며 비밀을 읽어 에이전트에 반환하지 않는다. `op run`으로 외부 MCP 서버를 감싸는 방식에서는 그 서버 프로세스가 실제 값을 받는다. ZeroPW의 도구도 값 조회 없이 설계한다. [S3] |
| SDK와 AI 통합 | 공식 튜토리얼도 모델에 원시 자격증명을 노출하는 위험을 경고한다. SDK의 값 조회 기능을 그대로 에이전트에 노출하지 않는다. [S4] |
| Service Accounts | 자동화용 접근 권한을 좁힐 수 있지만 계정 토큰 자체를 보호해야 한다. ZeroPW는 workload identity와 제한된 사용 권한을 우선한다. [S5] |
| SSH agent | 키 파일 내보내기 대신 인증·서명 기능을 제공한다. 자격증명 대신 사용 동작을 제공하는 설계의 참고 대상이다. [S6] |
| Connect | 자체 인프라에서 접근하는 API·캐시 구성이다. 개인용 첫 버전에는 별도 범용 비밀 API·캐시 계층을 추가하지 않는다. [S7] |
| Agentic autofill | 별도 브라우저 에이전트 통합 기능이 있다. 이번 CLI·API 중심 범위에서는 제외한다. [S8] |

이는 1Password에 없는 보안을 모두 새로 발명한다는 주장이 아니다. 현재의 우선순위는 필요한 기능만 소유 가능한 형태로 만드는 것이다. 환경변수 주입의 한계에서 고정 작업 실행을 선택한 부분은 ZeroPW의 설계 판단이다.

## 7. 성공 기준과 검증 순서

첫 성공은 “키를 등록한 뒤, 에이전트가 승인된 실제 작업을 완료하며 대화·도구 응답·작업 공간에 원문이 남지 않는 것”이다. 먼저 가짜 자격증명과 통제된 시험 서버로 누출 경로를 공격한다. 기준을 통과한 다음 최소 권한의 개발용 자격증명으로 사용성을 검증한다.

- 정상 흐름: 비밀 등록, 연결 설정, native tool 호출, 제한된 결과 확인, 값 없는 감사 기록까지 이어진다.
- 차단 흐름: 임의 명령, 다른 환경·연결 접근, 외부 목적지 변경, 만료·회수·재사용 요청을 거부한다.
- 누출 점검: stdout·stderr·오류·추적·파일·아티팩트·네트워크·후속 agent 입력을 검사한다. 마스킹 성공만으로 통과시키지 않는다.
- 운영 점검: 만료·회수 시 실행 상태가 일관되고, 백업을 별도 환경에서 복구하며, 실패 시 키가 로그에 남지 않는다.

응답 속도, 월 운영비, 반복 작업의 승인 횟수도 기록한다. 수치 목표와 예산은 초기 클라우드 구성 및 첫 사용처를 정한 후 합의한다. 프로덕션 비밀 사용은 구현 검증과 보안 검토 이후의 별도 단계다.

## 8. 다음 의도 정렬
