Team installation and usage

ZeroPW team manual

A creates a shared environment and invites B. After B joins, secrets and connections synchronize. Each device then issues its own agent grants.

ZeroPW shares encrypted secrets such as API keys. Whole-file .env import and export are unsupported. Keep non-secret settings such as URLs in existing application configuration.

Applications that need raw keys, and database drivers without a dedicated integration, are unsupported. Start with synthetic credentials and a verified server.

A · Initial administratorExample VPN address: 10.8.0.2
B · Invited teammateExample VPN address: 10.8.0.3

Addresses and names are examples. Replace project team-app, environment dev, and team port 47420 with your team's settings. Restrict the port to the team network.

01
Everyone · Apple Silicon Mac

Install with Homebrew and check the demo

Run on a Mac with Homebrew installed. Tested on macOS 26.5; older versions are unverified.

brew tap telicity-ai/zeropw https://github.com/telicity-ai/zeropw
brew install telicity-ai/zeropw/zeropw
brew test telicity-ai/zeropw/zeropw
zeropw-demo

Check: the installed version is 0.1.0. The demo ends with All 47 checks passed.

If Homebrew is missing, follow the Official installation instructions. On ARM64 Linux, use the Archive installer. Linux Homebrew, Intel Mac and x86-64 Linux binaries are outside this verification scope.

02
A and B · Each person's trusted terminal

Create your vault and device keys

Run once on each device. During init, choose administrator and recovery passphrases and store them separately. Devices do not need to share passphrases.

export ZPW_STATE="$HOME/.local/share/zeropw"
zeropw-admin --state-dir "$ZPW_STATE" init
zeropw-admin --state-dir "$ZPW_STATE" team init

Do not initialize a device again if it is already set up. In each new terminal, first run export ZPW_STATE=…. Only a human handles this configuration and administrator commands.

03
A · Initial administrator

Create the shared environment and keep it running

On A, share the team-app/dev environment. Both devices must be on the same LAN or team VPN. The addresses below are examples.

zeropw-admin --state-dir "$ZPW_STATE" project create team-app
zeropw-admin --state-dir "$ZPW_STATE" team share \
  --project team-app --environment dev --name owner
zeropw-admin --state-dir "$ZPW_STATE" serve --team-listen 10.8.0.2:47420

Keep this terminal running. If serve is already running, stop it and restart with the team listener option.

04
A invites → B joins

Invite a teammate and join

A · Invite from a new trusted terminal

export ZPW_STATE="$HOME/.local/share/zeropw"
zeropw-admin --state-dir "$ZPW_STATE" team invite \
  --env team-app/dev --role user --name teammate --ttl 1h \
  --address 10.8.0.2:47420

Send the invitation only to B through a secure channel. It can be used once within one hour. Invite teammates who need secret-editing and invitation authority with --role admin.

B · Join from your own trusted terminal

zeropw-admin --state-dir "$ZPW_STATE" team join \
  '<ONE_TIME_INVITATION>' --project team-app --environment dev
zeropw-admin --state-dir "$ZPW_STATE" team status --env team-app/dev
zeropw-admin --state-dir "$ZPW_STATE" team members --env team-app/dev
zeropw-admin --state-dir "$ZPW_STATE" serve --team-listen 10.8.0.3:47420

On both A and B, run team members and compare device fingerprints. Keep B's serve running too.

Never put invitations in agent contexts, Git or public chats. Enrollment currently receives the invitation as a command argument, which may be visible in process arguments and shell history. Run it only in a human's trusted terminal.

05
A · Administrator

Register a secret and service connection

In a new trusted terminal on A, register one API key. Keep its file accessible only to the administrator. Replace the path and API address below with verified values.

zeropw-admin --state-dir "$ZPW_STATE" secret put \
  --id service-key --kind api_key --project team-app --environment dev \
  --value-file /trusted/path/service-key
zeropw-admin --state-dir "$ZPW_STATE" connection create-http \
  --id service-api --project team-app --environment dev --service team-service \
  --secret-id service-key --target https://api.example.com \
  --auth bearer --methods GET --path-prefixes /v1

Secrets are encrypted, and changes are signed for synchronization. Connection settings also synchronize. After a successful import, a human administrator safely removes any temporary plaintext file. api.example.com and /v1/items are illustrative examples, not a promise of service compatibility.

B · Check synchronization and metadata, not values

zeropw-admin --state-dir "$ZPW_STATE" team status --env team-app/dev
zeropw-admin --state-dir "$ZPW_STATE" secret list \
  --project team-app --environment dev
zeropw-admin --state-dir "$ZPW_STATE" connection list

Check that B's lists contain service-key and service-api. Do not print secrets or copy their plaintext between devices.

Before connecting real credentials, verify API, error and log paths that could reflect authentication material. Creating a connection does not prove safe service compatibility. Administrators also handle later secret changes; the user role cannot edit them.

06
A and B · Human administrator on each device

Issue agent grants on each device

Team enrollment does not create agent grants. Create a caller identity and a grant on each device. Tokens are device-local and do not synchronize.

zeropw-admin --state-dir "$ZPW_STATE" principal create \
  --id agent-1 --runtime my-device
zeropw-admin --state-dir "$ZPW_STATE" grant create \
  --principal agent-1 --connection service-api --ttl 1h --max-uses 100

Configure the agent runtime with only the once-printed caller token and the first JSON response from this device's serve process: its url field. Do not pass vault paths, administrator/recovery passphrases, invitations or original keys.

export ZEROPW_GATEWAY_URL="<THIS_DEVICE_SERVE_URL>"
export ZEROPW_CALLER_TOKEN="<THIS_DEVICE_CALLER_TOKEN>"

These lines illustrate human-managed runtime configuration. Never put actual tokens in documents, Git, chats or shell history. The URL is this device's loopback gateway. Do not use a teammate's VPN address as the agent gateway. Grants issued before sharing an existing environment may become stale and need reissuing.

07
Agent · Without original secrets

Use a connection from the agent

Agent commands start here. Configure the service and its allowed scope once; do not register every operation within that scope.

zeropw-agent list-connections
zeropw-agent request --connection service-api --method GET --path /v1/items

Setup is complete when the connection appears and the verified API returns its expected business response. This example allows only the GET /v1 scope.

CLI and SSH execution

Use only an administrator-verified CLI profile or SSH connection. Replace the ID and arguments below with actual settings. After --, pass arguments to the configured program, not a replacement executable path.

zeropw-agent exec --connection '<CONNECTION_ID>' -- '<PROFILE_ARGUMENTS>'
zeropw-agent status --run '<RETURNED_RUN_ID>'
zeropw-agent cancel --run '<RETURNED_RUN_ID>'

exec acceptance is not completion. Check the returned run ID until it reaches a terminal state. SSH requires OpenSSH 8.9 or later and verified host keys/session binding. Cancellation does not guarantee termination of a remote process.

Install the Codex skill (optional)

Download SKILL.md for v0.1.0 and place it at ~/.codex/skills/zeropw-agent/SKILL.md. If CODEX_HOME is set separately, use its skills/zeropw-agent/ directory. Compare an existing skill before replacing it. Never add keys or invitations to the skill.

$zeropw-agent List available connections and retrieve /v1/items using service-api.

Give each agent the common prompt below, changing only the A/B role. Exchange the result JSON objects, then compare them with Prompt 2. Never include invitations or caller tokens in exchanged results.

Result exchange verifies a connection. It does not replace initial enrollment, which requires a one-time invitation passed securely between humans.

All failed_checks and human_next_actions values must match ^[a-z0-9_.-]{1,96}$, with no uppercase role prefix or prose. Use local_result_not_pass for a blocked local result and rejected_commits_nonzero for any rejection. Its actions are review_quarantine_records, confirm_identical_accepted_commit, confirm_author_approved_at_acceptance, confirm_rejection_set_stable. Never suggest clearing rejection history to obtain ready. Use the checker vocabulary in onboarding-validator.md; stale evidence returns blocked.

Both local checks must pass, and environments, members and vectors must match before returning ready. Unknown checks are not passes. This verifies onboarding at one point in time, not production security or ongoing connectivity.

Result JSON must pass the independent validator using a separately approved policy. See the artifact receipt and JSON Schema. The current v0.1.0 enrollment test is blocked by retained rejection history; a ready pair has not been established.

Operational notes

  • serve must be running for synchronization. Offline devices can keep using their previous state; revocation waits for reconnection.
  • Invite only trusted people. The trusted process on a user device can also decrypt shared secrets.
  • Removing a member cannot erase previously accessible keys. Rotate them at the external provider. If rejected_removals appears, an active administrator must review the targets and reissue the intended removal.
  • Do not run team compact during initial enrollment. Transfer of compacted snapshots to new devices is not implemented.
  • Running the vault and agent as the same OS user does not provide isolation. Prepare separate isolation before using real credentials. The agent tools API currently accepts only loopback connections.
