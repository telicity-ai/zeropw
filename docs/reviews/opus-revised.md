# ZeroPW 적대적 재리뷰 (Opus) — 2026-09-11

**판정: PASS (의도 정렬 한정, 조건부)**

이전 리뷰가 의도 정렬 차단으로 지목한 3건(A-1 데이터 보호 범위, A-2 사람 신뢰 앵커, A-3 호환 모드 격리)은 문서에 모두 반영됐다. 남은 항목은 제품 의도와 모순되지 않으며, 구현 착수 전에 답해야 할 **범위 결정 2건**과 **출시 차단 엔지니어링 인수 기준**이다.

> **이 문서는 설계 리뷰이며 보안 인증이 아니다.** 침투 테스트·코드 감사·위협 모델링 워크숍·규제 인증을 대체하지 않는다. 여기서의 PASS는 "의도가 일관되게 문서화됐다"는 뜻이며 구현물의 안전성이나 배포 승인을 뜻하지 않는다. [S1]–[S8]은 도구 없이 검증하지 않았다.

## A. 구현 착수 전 사용자 결정이 필요한 항목

### 1. 저장 가능한 비밀의 등급 제한이 없다 — 자기참조 권한 상승 — **high**
- 위치: `product-intent.md` §1·§5(비밀 관리) / `security-design.md` §2
- 문제: 문서는 "환경변수·API 키·비밀번호"를 무제한으로 받는다. **ZeroPW 자신의 통제면 자격증명**(클라우드 계정 API 키, IAM/KMS 관리 키, 도메인·DNS, 결제, 백업 버킷, 모델 provider 키)을 넣지 말라는 조항이 없다.
- 익스플로잇: 사용자가 편의로 클라우드 계정 키를 등록하고 사람이 `cloud.account_status` 같은 읽기 어댑터를 승인한다. 이후 어댑터 인자 확장 PR 하나 또는 승인 화면에서의 한 번의 오클릭이면, 실행기가 **자기 신뢰 경계(KMS 키 정책, 감사 버킷, 실행기 role)** 를 조작할 수 있는 자격증명을 이미 쥐고 있는 상태가 된다. design §2의 "agent·하네스 신원의 IAM 조작 금지"는 *클라우드 IAM 주체*에 대한 제약이지, *저장된 제3자 자격증명이 같은 계정을 조작하는 경로*를 막지 않는다. MVP가 단일 계정이라 이 경로는 곧바로 전체 침해다.
- 최소 수정: intent §5 또는 design §2에 1행 — "ZeroPW의 인프라·KMS·비밀 저장소·감사/백업·결제·도메인·모델 provider 자격증명은 저장 대상 및 연결 대상에서 제외한다."

### 2. v1 결과 필드 제한과 "첫 검증 = 저장소 메타데이터 읽기"가 서로 긴장 관계 — **high**
- 위치: `product-intent.md` §5 / `security-design.md` §4 (v1 결과 필드 문단)
- 문제: design은 v1 반환을 enum·불리언·범위 제한 정수·서버 생성 ID·타임스탬프로 못 박고 "외부 자유 텍스트 반환 금지"를 선언했다. 그런데 intent는 첫 검증 작업으로 "저장소 메타데이터 읽기"를 든다. 메타데이터의 실용적 필드(브랜치명, description, 마지막 커밋 메시지)는 전부 **공격자 영향 가능한 자유 텍스트**다.
- 익스플로잇: 어댑터 구현 시 "브랜치명은 메타데이터지 자유 텍스트가 아니다"라는 해석이 끼어들면 B-4(외부 콘텐츠 주입)가 그대로 부활한다. 계약 문장이 해석 여지를 남긴 상태다.
- 제품 트레이드오프: 이 제한을 지키면 v1이 사용자에게 주는 답은 사실상 "예/아니오/개수"뿐이다. 이 수준이 원하는 사용 경험인지 확인이 필요하다.
- 최소 수정: intent §5에 첫 어댑터 반환 필드를 열거(예: `reachable`, `default_branch_exists`, `open_pr_count`, `last_push_age_bucket`). 자유 텍스트가 필요하다고 판단되면 별도 "데이터 노출 정책"을 먼저 확정한 뒤 어댑터를 만든다고 명시.

## B. 출시 차단 엔지니어링 인수 기준 (문서 계약 문장으로 선반영)

### 3. 사전 허용(standing pre-auth)의 결합 범위가 명시 승인보다 약하다 — **high**
- 위치: `security-design.md` §5 (1문단 vs 4문단)
- 문제: 명시 승인은 "호출자·프로젝트·환경·연결·비밀 버전·어댑터 digest·입력 hash·대상·만료·횟수"에 결합한다. 반면 사전 허용은 "환경·대상·만료·횟수"만 언급된다.
- 익스플로잇: 어댑터가 새 digest로 갱신되거나 사용자가 키를 교체(새 비밀 버전 등록)한 뒤에도, 옛 사전 허용이 새 코드·새 자격증명으로 무승인 자동 실행을 계속한다. §5의 "승인 전후 코드·입력 변경 시 새 요청"이 사전 허용 경로에는 적용되지 않는 것으로 읽힌다.
- 최소 수정: §5에 "사전 허용도 어댑터 digest·연결·비밀 버전에 결합하며, 이 중 하나라도 바뀌면 자동 무효화되고 사용자가 다시 켠다."

### 4. Astra가 "보안 쟁점"과 "일반 이견"을 스스로 분류한다 — **medium**
- 위치: `harness.md` §1(역할 표), §2
- 문제: A-2 수정으로 "보안 쟁점은 사용자 보고"가 들어왔지만, 무엇이 보안 쟁점인지 판단하는 주체가 여전히 문서 작성자 겸 재정자인 Astra다. §2의 "근거 없이 PASS로 바꾸지 않는다"도 자기 판정형 조건이다.
- 익스플로잇: 어댑터 인자 범위 확대나 egress 대상 추가에 대한 리뷰 반대를 "설계 취향 차이=일반 이견"으로 분류해 사용자 보고 없이 종결한다. 사람 승인 게이트는 남지만, 사용자는 반대 의견이 있었다는 사실을 모른 채 승인 화면만 본다.
- 최소 수정: §1에 "분류 권한은 리뷰어의 severity 라벨에 귀속한다. Opus가 Critical/High로 표기한 항목은 Astra의 재정 대상이 아니며, 해결 증거 없이는 사용자 보고 후 사용자가 결정한다."

### 5. "반복 실행에 새 승인 불요" 조항의 범위가 열려 있다 — **medium**
- 위치: `harness.md` §3 마지막 문장
- 문제: 승인이 변경 digest에 결합된다고 해놓고 곧바로 "사전에 승인된 작업을 반복 실행할 때마다 새 승인을 요구한다는 뜻은 아니다"로 닫는다. "작업"의 단위가 digest인지 작업 종류(예: 어댑터 등록 일반)인지 불명확하다.
- 익스플로잇: 한 번 받은 "어댑터 등록 승인"을 종류 단위로 해석해 후속 어댑터 등록을 무승인 처리한다. A-2 수정의 핵심이 무력화된다.
- 최소 수정: "동일 digest·동일 정책 범위의 재실행만 해당하며, digest·대상·egress·정책 범위가 바뀌면 새 승인이다."

### 6. 전역 중지와 이상 사용량 통지가 없다 — **medium**
- 위치: `security-design.md` §5·§6 / `product-intent.md` §7
- 문제: 회수는 연결·권한 단위이고, 사전 허용 범위 안의 반복 호출은 만료·횟수 한도까지 정상 동작으로 취급된다. 사용자가 그 사이 상황을 아는 경로와 한 번에 멈추는 수단이 문서에 없다.
- 익스플로잇: 주입된 에이전트가 한도 소진까지 조용히 반복 호출해 허용 데이터를 모으고 외부 대상에 요청을 쌓는다. 사용자는 사후 감사 기록에서만 발견한다.
- 최소 수정: §5에 "전체 실행 즉시 정지 스위치(모든 신규 실행 거부)와, 사전 허용 한도 소진율·비정상 호출 패턴에 대한 사용자 알림을 둔다."

### 7. [S1]–[S8] 인용 증거 부재가 그대로다 — **medium**
- 위치: `product-intent.md` §6, `harness.md` §5
- 문제: §6 표는 "확인한 동작"이라고 단정하지만 근거는 URL뿐이다. 8개 링크가 단일 호스트에 균일한 경로 패턴으로 나열돼 있어, 조사 서브에이전트 생성물일 가능성을 문서 자체로는 배제할 수 없다. 리뷰어는 검증할 수단이 없다.
- 영향: [S3]/[S4]가 "공식 안내도 원문 반환을 피한다"라는 설계 정당화에 쓰인다. 근거가 틀리면 문단이 붕괴한다(설계 판단 자체는 독립적으로 성립하므로 medium).
- 최소 수정: 각 항목에 조회 시각·HTTP 상태·인용 1행을 부록으로 남기거나, 확보 전까지 "미검증 인용"으로 표기.

### 8. 미확정 어조로 남은 인수 기준 — **low**
- 위치: `security-design.md` §2("별도 계정 분리는 우선 검토"), §6("감사 장애 시 거부하는 방향을 제안한다")
- 문제: fail-closed와 계정 분리는 위 #1·#3의 영향 범위를 좌우하는데 "제안/검토" 수준이다. 구현 설계에서 조용히 뒤집힐 수 있다.
- 최소 수정: "감사·승인 시스템 장애 시 신규 비밀 사용 거부는 인수 기준이다"로 확정 표현 전환. 계정 분리는 결정 기한을 기재.
