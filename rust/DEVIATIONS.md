# Recorded deviations from the Python prototype

Only deviations allowed by `PORTING.md` §3 or explicitly justified here. One row per behaviour.

| Module | Python behaviour | Rust behaviour | Reason |
| --- | --- | --- | --- |
| crypto | Hand-written RFC 8439 / RFC 8032 in pure Python, not constant time | `chacha20poly1305`, `ed25519-dalek` crates | PORTING.md §3.1 |
| all | Secret `bytes` cannot be zeroised | `SecretBytes` zeroised on drop, redacted `Debug` | PORTING.md §3.2 |
| crypto/chacha20poly1305 | `chacha20_block`'s `counter: int` is runtime-checked (rejects negative, non-int, float, or `>= 2**32`, raising `TypeError`/`ValueError`) | `counter: u32`, so those cases are compile-time impossible; only the key/nonce size checks remain runtime errors | Rust's type system already enforces the RFC's 32-bit unsigned counter range; no runtime check can express something the type doesn't allow |
| crypto/chacha20poly1305, crypto/ed25519, crypto/x25519 | `decrypt`/`sign`/`verify`/`public_key_from_seed`/`scalarmult`/`shared_secret`/`public_key` accept `bytes \| bytearray \| memoryview` and raise `TypeError` (or, for `decrypt`, `AuthenticationError`) for a non-bytes-like value or a released `memoryview` | Functions take `&[u8]` directly; a caller cannot construct an "unusable buffer" value, so this whole error class does not exist | `&[u8]` is always a valid, live view; the Python cases exist only because `bytes`-like arguments are duck-typed and mutable buffers can be released after construction |
| kms | `LocalFileKms.create`: if `os.open(..., O_EXCL)` loses a TOCTOU race after the initial `path.exists()` check, or `path.parent.mkdir` fails for another OS reason, the raw `OSError`/`FileExistsError` propagates uncaught (not wrapped as `KmsError`) | Both cases are wrapped as `KmsError("kms_create_failed", <os error text>)` | `Result<T, crate::errors::Error>` has no "let anything else escape" case the way Python's unchecked exceptions do; wrapping keeps the return type uniform. | pyjson | `json.dumps`/`json.dump` default to `allow_nan=True`: a non-finite float serializes as bare `NaN`/`Infinity`/`-Infinity`, and `json.load`/`json.loads` accept those bare tokens back. | pyjson | A JSON string containing an unpaired UTF-16 surrogate `\u` escape (e.g. `"\ud800"`, a lone high surrogate with no following low surrogate) is valid per the JSON grammar (which allows any `\uXXXX`); CPython's decoder accepts it, producing a `str` containing a lone surrogate code point (not valid Unicode text, but a legal Python `str`) | `pyjson::loads` rejects any lone (unpaired) surrogate `\u` escape as a parse error before handing the text to `serde_json` -- coordinator ruling PORTING.md §3.6 | Rust `String`/`char` cannot represent an unpaired surrogate (it is not a valid Unicode scalar value); `serde_json` itself silently substitutes U+FFFD REPLACEMENT CHARACTER for one instead of erroring, which is not caught elsewhere in this crate, so `pyjson::loads` pre-scans for this case explicitly. A state file that somehow contained one would load (as `str` with an unpaired surrogate) in Python but be rejected (`state_corrupt` for a state file, or the caller's own malformed-input error for a peer/agent message) in Rust, per §3.6 |
| pyjson (`loads`/`dumps`/`Value` clone-compare-drop, findings A-R3-1, A-R4-1, A-R5-1, A-R5-2) | CPython's own recursion ceilings, confirmed directly against `python3.12` on this port's own test environment (not asserted from memory, and re-measured for round 5 rather than trusted from a prior round's numbers): `json.loads` and compact `json.dumps` both raise `RecursionError` only at depth 9,998 (last accepted: 9,997); `json.dump(doc, stream, sort_keys=True, indent=2)` -- exactly `StateDir.write_json`'s call -- raises it already at depth 996 (last accepted: 995), measured both standalone and through the real `StateDir.write_json` API itself (both gave the same boundary in this environment; the equivalence reviewer's own framing that this ceiling is caller-frame-dependent in general still holds -- it is not a fixed language constant, just one that happened to land on the same number here). Both changes were forced by the same finding: round 4's fix (an explicit depth check before recursing into `write_value`, with `MAX_JSON_DEPTH` = 1,000 chosen to leave margin under `write_value`'s own measured ~1,100-1,150-level hazard zone *on an empty 2 MiB stack*) narrowed but did not remove the hazard -- measured directly this round: rendering a 1,000-level document costs 1.835-1.966 MiB of stack (debug/test profile), and on a 2 MiB stack that a caller had already used 262,144 bytes of before ever calling `dumps` (every real request-handling thread in this crate -- `fake_upstream.rs`, `signer.rs` -- uses the platform default 2 MiB stack and does real work of its own first), depth 1,000 reliably aborted the whole process while 800 and 900 were still fine at that same pre-used amount. `MAX_JSON_DEPTH` = 500 was chosen because it is comfortably above every depth this port's own tests require (128-500) and, combined with the new dedicated-stack tier for anything above 200, gives real headroom on a realistically-pre-used 2 MiB stack rather than only an idle one; it is also now strictly below (not merely "a shade more conservative than", the previous, backwards-and-numerically-wrong framing) CPython's own tightest real ceiling for the exact write path this port's persistence relies on (995, see the Python-behaviour column) -- 500 is comfortably under 995, not close to it, so every document this port's `StateDir::write_json` ever persists is also one Python's own `StateDir.write_json` could have written, closing finding A-R5-2 with real margin rather than a near-miss. `dumps` itself still has its explicit, non-recursive (heap-stack-based) depth check, `value_depth_within`, run before any rendering at all. A document nested past `MAX_JSON_DEPTH` is not something any writer in this crate, or the matching Python prototype, ever produces.
