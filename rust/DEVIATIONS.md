# Recorded deviations from the Python prototype

Only deviations allowed by `PORTING.md` §3 or explicitly justified here. One row per behaviour.

| Module | Python behaviour | Rust behaviour | Reason |
| --- | --- | --- | --- |
| crypto | Hand-written RFC 8439 / RFC 8032 in pure Python, not constant time | `chacha20poly1305`, `ed25519-dalek` crates | PORTING.md §3.1 |
| all | Secret `bytes` cannot be zeroised | `SecretBytes` zeroised on drop, redacted `Debug` | PORTING.md §3.2 |
| crypto/chacha20poly1305 | `chacha20_block`'s `counter: int` is runtime-checked (rejects negative, non-int, float, or `>= 2**32`, raising `TypeError`/`ValueError`) | `counter: u32`, so those cases are compile-time impossible; only the key/nonce size checks remain runtime errors | Rust's type system already enforces the RFC's 32-bit unsigned counter range; no runtime check can express something the type doesn't allow |
| crypto/chacha20poly1305, crypto/ed25519, crypto/x25519 | `decrypt`/`sign`/`verify`/`public_key_from_seed`/`scalarmult`/`shared_secret`/`public_key` accept `bytes \| bytearray \| memoryview` and raise `TypeError` (or, for `decrypt`, `AuthenticationError`) for a non-bytes-like value or a released `memoryview` | Functions take `&[u8]` directly; a caller cannot construct an "unusable buffer" value, so this whole error class does not exist | `&[u8]` is always a valid, live view; the Python cases exist only because `bytes`-like arguments are duck-typed and mutable buffers can be released after construction |
| kms | `LocalFileKms.create`: if `os.open(..., O_EXCL)` loses a TOCTOU race after the initial `path.exists()` check, or `path.parent.mkdir` fails for another OS reason, the raw `OSError`/`FileExistsError` propagates uncaught (not wrapped as `KmsError`) | Both cases are wrapped as `KmsError("kms_create_failed", <os error text>)` | `Result<T, crate::errors::Error>` has no "let anything else escape" case the way Python's unchecked exceptions do; wrapping keeps the return type uniform. Only the initial `path.exists()` check (`KmsError("kms_exists", ...)`) is reachable in the crate's own tests |
| pyjson | `json.dumps`/`json.dump` default to `allow_nan=True`: a non-finite float serializes as bare `NaN`/`Infinity`/`-Infinity`, and `json.load`/`json.loads` accept those bare tokens back. Separately, a numeric literal with a `.`/exponent whose magnitude overflows `float` (e.g. `1e400`) parses via CPython's `float()` to `inf`/`-inf` with no exception, and `json.dumps` on that value later writes the bare `Infinity`/`-Infinity` token | `pyjson::dumps` returns an error for a non-finite float (a bare `NaN`/`Infinity` token, *or* a `Number` whose value overflows to infinity) instead of writing it; `pyjson::loads` rejects the bare tokens *and* any numeric literal that would overflow to a non-finite `f64` as a parse error (none of these are valid RFC 8259 JSON, and `serde_json` does not accept the bare tokens even in `arbitrary_precision` mode) | No writer in `zeropw/` ever produces a non-finite float or an overflowing numeric literal: audit fields are `round(time.time(), 3)`-derived (always finite, always in `f64` range), and no vault/policy/handle document holds a float at all. Unreachable in practice; if a future module needs to persist a non-finite float, extend `pyjson` (both directions) before relying on it for that write. A state file that somehow contained a bare `NaN`/`Infinity` token, or an overflowing numeric literal, would load in Python but `state_corrupt` in Rust. |
| pyjson | A JSON string containing an unpaired UTF-16 surrogate `\u` escape (e.g. `"\ud800"`, a lone high surrogate with no following low surrogate) is valid per the JSON grammar (which allows any `\uXXXX`); CPython's decoder accepts it, producing a `str` containing a lone surrogate code point (not valid Unicode text, but a legal Python `str`) | `pyjson::loads` rejects any lone (unpaired) surrogate `\u` escape as a parse error before handing the text to `serde_json` -- coordinator ruling PORTING.md §3.6 | Rust `String`/`char` cannot represent an unpaired surrogate (it is not a valid Unicode scalar value); `serde_json` itself silently substitutes U+FFFD REPLACEMENT CHARACTER for one instead of erroring, which is not caught elsewhere in this crate, so `pyjson::loads` pre-scans for this case explicitly. A state file that somehow contained one would load (as `str` with an unpaired surrogate) in Python but be rejected (`state_corrupt` for a state file, or the caller's own malformed-input error for a peer/agent message) in Rust, per §3.6 |
| pyjson (`loads`/`dumps`/`Value` clone-compare-drop, findings A-R3-1 and A-R4-1) | CPython's own recursion ceilings, confirmed directly against `python3.12` (not asserted from memory): `json.loads` and compact `json.dumps` both raise `RecursionError` only at depth 9,997; `json.dump(doc, stream, sort_keys=True, indent=2)` -- exactly `StateDir.write_json`'s call -- raises it far earlier, at depth 994. Python has no separate "clone" primitive for a parsed document (a `dict`/`list` tree is copied structurally, not via one recursive operation the way `Value::clone()` is) | `pyjson::loads` accepts array/object nesting up to `MAX_JSON_DEPTH` (1,000) and `pyjson::dumps` accepts and renders the same bound -- both reject anything deeper as malformed/invalid input, where CPython would keep going for several thousand more levels via `loads`/compact `dumps` (though not via the indent+sort_keys form `write_json` itself uses, whose own real ceiling of 994 this port's bound already sits close to) | Four separate operations recurse over a `Value` tree using native call-stack frames, each hazardous on its own 2 MiB-stack thread at a different depth (all measured by development-time/reviewer probing, unoptimized/debug build): **building** (`serde_json`'s deserializer) overflows between roughly 800-900 levels; **serializing** (`pyjson::write_value`, this crate's own code -- finding A-R4-1's regression: round 3 fixed `loads` but left this path, and the four below, unbounded) overflows between roughly 1,100-1,150 levels; **cloning** (`Value`'s derived `Clone`) overflows around 1,800-1,805 levels; **comparing** (`Value`'s derived `PartialEq`/`==`) overflows around 4,876-4,877 levels; **dropping** (`Value`'s derived `Drop` glue, run whenever and on whatever thread a caller lets a `Value` go out of scope, entirely outside this module's control) overflows around 8,780-8,781 levels. Only the first of these (building, inside `loads`) can be steered onto a dedicated large-stack thread from here (`parse_on_dedicated_stack`, 64 MiB, used for any document deeper than `SAFE_INLINE_DEPTH` (200)); `dumps` is also called on values this crate builds directly (never through `loads`), and clone/compare/drop happen at arbitrary call sites this module cannot intercept, so the only available lever over those four is capping every `Value` this crate ever constructs or accepts, via one shared `MAX_JSON_DEPTH`, safely under the *tightest* of the four -- serializing, at ~1,100 -- which by construction gives the other three (with far larger margins) the same safety without needing a dedicated stack for them at all. `dumps` itself gained an explicit, non-recursive (heap-stack-based, so it cannot itself overflow) depth check, `value_depth_within`, run before any recursive rendering. `MAX_JSON_DEPTH` = 1,000 sits at or above the 900-level probe this port's own tests require, comfortably under every measured hazard above, and a shade more conservative than CPython's own tightest real ceiling for the exact write path this port's persistence relies on (994). See `pyjson.rs`'s module doc, "Recursion / nesting depth" section, for the full reasoning. A document nested past `MAX_JSON_DEPTH` is not something any writer in this crate, or the matching Python prototype, ever produces.
