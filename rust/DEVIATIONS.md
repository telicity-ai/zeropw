# Recorded deviations from the Python prototype

Only deviations allowed by `PORTING.md` §3 or explicitly justified here. One row per behaviour.

| Module | Python behaviour | Rust behaviour | Reason |
| --- | --- | --- | --- |
| crypto | Hand-written RFC 8439 / RFC 8032 in pure Python, not constant time | `chacha20poly1305`, `ed25519-dalek` crates | PORTING.md §3.1 |
| all | Secret `bytes` cannot be zeroised | `SecretBytes` zeroised on drop, redacted `Debug` | PORTING.md §3.2 |
| crypto/chacha20poly1305 | `chacha20_block`'s `counter: int` is runtime-checked (rejects negative, non-int, float, or `>= 2**32`, raising `TypeError`/`ValueError`) | `counter: u32`, so those cases are compile-time impossible; only the key/nonce size checks remain runtime errors | Rust's type system already enforces the RFC's 32-bit unsigned counter range; no runtime check can express something the type doesn't allow |
| crypto/chacha20poly1305, crypto/ed25519, crypto/x25519 | `decrypt`/`sign`/`verify`/`public_key_from_seed`/`scalarmult`/`shared_secret`/`public_key` accept `bytes \| bytearray \| memoryview` and raise `TypeError` (or, for `decrypt`, `AuthenticationError`) for a non-bytes-like value or a released `memoryview` | Functions take `&[u8]` directly; a caller cannot construct an "unusable buffer" value, so this whole error class does not exist | `&[u8]` is always a valid, live view; the Python cases exist only because `bytes`-like arguments are duck-typed and mutable buffers can be released after construction |
| kms | `LocalFileKms.create`: if `os.open(..., O_EXCL)` loses a TOCTOU race after the initial `path.exists()` check, or `path.parent.mkdir` fails for another OS reason, the raw `OSError`/`FileExistsError` propagates uncaught (not wrapped as `KmsError`) | Both cases are wrapped as `KmsError("kms_create_failed", <os error text>)` | `Result<T, crate::errors::Error>` has no "let anything else escape" case the way Python's unchecked exceptions do; wrapping keeps the return type uniform. Only the initial `path.exists()` check (`KmsError("kms_exists", ...)`) is reachable in the crate's own tests |
| pyjson (all `json.dumps` call sites without `sort_keys=True`) | `dict` preserves insertion order; `json.dumps(payload)` (no `sort_keys`) emits keys in insertion order | `serde_json::Map` is `BTreeMap`-backed in this build, so object keys are **always** emitted in ascending sorted order, regardless of `DumpOptions::sort_keys` | `serde_json`'s `preserve_order` feature (insertion-ordered `Map`, needed to match Python for the few call sites that omit `sort_keys`) depends on the `indexmap` crate, which is not present in the offline `cargo` registry cache used for this build (`cargo check --offline` fails with `no matching package named 'indexmap' found`) and PORTING.md requires `cargo test --offline`. Every call site this half of the port owns already passes `sort_keys=True` (see `pyjson.rs` module doc), so this is unobservable today; it only affects a future second-half port of `agent_cli.py`'s plain `json.dumps(payload)` (and similar), which should either add `indexmap` once the registry cache allows it, or explicitly sort payload keys to match. |
| pyjson | `json.dumps`/`json.dump` default to `allow_nan=True`: a non-finite float serializes as bare `NaN`/`Infinity`/`-Infinity`, and `json.load`/`json.loads` accept those bare tokens back | `pyjson::dumps` returns an error for a non-finite float instead of writing those tokens; `pyjson::loads` rejects them as a parse error (they are not valid RFC 8259 JSON, and `serde_json` does not accept them even in `arbitrary_precision` mode) | No writer in `zeropw/` ever produces a non-finite float: audit fields are `round(time.time(), 3)`-derived (always finite), and no vault/policy/handle document holds a float at all. Unreachable in practice; if a future module needs to persist a non-finite float, extend `pyjson` (both directions) before relying on it for that write. A state file that somehow contained a bare `NaN`/`Infinity` token would load in Python but `state_corrupt` in Rust. |
| handles | `HandleIssuer.verify` decodes the payload with `str(payload["c"])` / `int(payload["pv"])` etc., which coerces almost any JSON scalar (e.g. a JSON `null` for `"c"` stringifies to `"None"`; a JSON float for `"pv"` coerces via `int()`) | `handles::parse_payload` requires the exact expected JSON type (string for `c`/`n`/`g`/`jti`; integer for `v`/`pv`/`iat`/`exp`) and treats any other type as `handle_malformed` | The payload is only reached after the HMAC signature over it has already been verified, so a payload exploiting Python's looser coercion can only be produced by someone who already holds the signing key -- narrowing Python's error behaviour for a hand-crafted, differently-typed (but validly signed) token does not weaken the security boundary. `HandleIssuer::issue` (this port and Python's) only ever emits well-typed payloads, so this is unobservable for any token either implementation issues, including the cross-language oracle tests in `handles.rs`. |
| audit | `Audit.tail`/`Audit.alerts` call `json.loads(line)` directly with no `try`/`except`: a corrupt line raises an uncaught `json.JSONDecodeError` (a `ValueError`, not one of the `errors.py` classes -- it is not `except ZeroPWError`-catchable) | `Audit::tail`/`Audit::alerts` map a corrupt line to `Error::state("state_corrupt")` | Rust's `Result<T, Error>` needs a concrete error type; there is no equivalent of letting an unrelated stdlib exception escape uncaught. `Audit::iter_records` already matches Python exactly (both silently skip an unparseable line), so this only affects the two capped readers, and only when the log file itself is corrupted (disk corruption, a write truncated mid-line) -- `record`/`_alert` always write one complete, valid JSON line per call, so this crate cannot produce a corrupt line itself. |
| crypto/x25519 | Hand-written RFC 7748 Montgomery ladder in pure Python, not constant time | `x25519-dalek` / `curve25519-dalek` crates (`x25519_dalek::x25519`, which clamps via `clamp_integer` and decodes `u` the same way) | PORTING.md §3.1; RFC 7748 §5.2/§6.1 test vectors from `tests/test_x25519.py` still pass byte-for-byte |
| crypto/x25519 | `clamp_scalar(raw: bytes) -> int`: returns the clamped scalar as a Python arbitrary-precision `int` | `clamp_scalar(raw: &[u8]) -> Result<[u8; 32], SizeError>`: returns the same 255-bit value's little-endian byte encoding | Rust's `std` has no size-agnostic bignum; every caller (including this module's own tests) treats the two representations identically, so the value carried is unchanged |
| crypto/x25519 | `clamp_scalar` has no length check on `raw`: a shorter input raises `IndexError` at `k[31]`, a longer one is silently accepted and changes the `int.from_bytes` magnitude instead of erroring | `clamp_scalar` rejects any input whose length is not exactly 32 bytes with `SizeError`, mirroring the length check `scalarmult`'s `_as_bytes` already performs for its own arguments | Engineering rule: no panics or silent mis-computation on untrusted input; `clamp_scalar` is never called with a wrong-length argument by the Python prototype's own call sites, so this only closes a latent gap |
| crypto/x25519 | `shared_secret`'s all-zero check is a plain `int.from_bytes(result, "little") == 0` comparison (not constant time) | Compares via `subtle::ConstantTimeEq` against an all-zero array | PORTING.md §3.3 (secret comparisons are constant time); the compared value is a computed Diffie-Hellman result, so this only strengthens the Python behaviour |
| sshwire | `Ed25519PrivateKey.__eq__` compares seeds with ordinary `bytes.__eq__` | `Ed25519PrivateKey::eq` compares seeds with `SecretBytes::ct_eq` (constant time) | PORTING.md §3.3 |
| sshwire | `encode_uint32(n)` takes any `int` and raises `ValueError` for `n < 0` or `n > 0xFFFFFFFF` | `encode_uint32(n: u32)`: out-of-range values are unrepresentable, enforced at compile time instead of at runtime | Stronger (static) enforcement of the same invariant; no behaviour is reachable that Python would reject and Rust would accept |
| sshwire | `encode_string`/`Reader` raise `TypeError` for a non-`bytes`/`str` argument | `encode_string` takes `impl AsRef<[u8]>`; a wrong argument type is a compile error | Same reasoning as `encode_uint32`: the invalid case is unrepresentable rather than runtime-checked |
| sshwire | `Reader.raw(n)` raises `ValueError` for `n < 0` | `Reader::raw(n: usize)`: negative lengths are unrepresentable | Same reasoning |
| sshwire | `AgentConnection`/`read_agent_message`/`write_agent_message` accept any duck-typed object with `.recv`/`.sendall` (or a bare callable), raising `TypeError` otherwise; `AgentConnection` is a context manager with an explicit `.close()` | Generic over `std::io::Read`/`Write`; a wrong type is a compile error. No `.close()`: the wrapped stream closes when the `AgentConnection` is dropped (RAII), the idiomatic Rust equivalent of `__exit__` | PORTING.md §3.4 ("Python-only mechanisms become explicit seams with identical behaviour"); observable protocol behaviour (framing, EOF vs. transport-error handling, `MAX_AGENT_MESSAGE`) is unchanged |
| sshwire | RFC 4251 `mpint` operates on Python's arbitrary-precision `int` | A minimal local `MpInt` (sign + big-endian magnitude `Vec<u8>`) implements exactly the operations `mpint` needs (bit length, two's-complement encode/decode); no general arithmetic (`+`, `*`, ...) | `mpint` is the only place in ZeroPW that needs a bignum (Ed25519 never uses it) and no other in-scope module calls it, so a general-purpose bignum crate would be pure surface area for one encoder/decoder pair. Encoding equivalence with Python for values that don't fit any native Rust integer (`2**255`, `2**4096 + 12345`, ...) is checked directly against the Python oracle in `src/sshwire.rs`'s test `mpint_round_trip_matches_python_for_large_values` |
| sshwire | `authorized_keys` field-separator validation rejects any `str.isspace()` character other than space/tab; Python's `str.isspace()` covers Unicode `Zs`/`Zl`/`Zp` plus the bidirectional-class-`B` ASCII separators `\x1c`-`\x1f` | `py_isspace` approximates this as Rust's `char::is_whitespace()` (Unicode `White_Space` property, which already includes `\x85` NEL) plus an explicit `\x1c..=\x1f` range | Replicating CPython's exact `str.isspace()` table is out of scope for a prototype port; the approximation covers every character exercised by `test_only_ascii_space_and_tab_separate_fields`'s `EXOTIC_WHITESPACE` table and differs from Python only for obscure Unicode categories no test (or real `authorized_keys` line) exercises |
| sshwire | `WireError`/`UnsupportedKeyType` are an exception subclass pair (`except UnsupportedKeyType` vs. `except WireError`); `Ed25519PublicKey.to_authorized_key`'s comment check and `encode_string`'s over-length check instead raise a *bare* `ValueError`, which is **not** a `WireError` instance, so a Python `except WireError` does not catch it | A single `WireError` struct tags each case with a three-way `kind` (`class_name()` returns `"WireError"`, `"UnsupportedKeyType"`, or `"ValueError"`; `is_wire_error()` is `false` only for the `ValueError` tag, `is_unsupported()` only for `"UnsupportedKeyType"`) | Coordinator ruling PORTING.md §3.5 applies downstream: `Vault._public_metadata` (not yet ported) catches only `sshwire.WireError`, so a comment containing `\n`/NUL must stay distinguishable from an ordinary `WireError` all the way to that call site. `WireError::value_error(...)` marks the two bare-`ValueError` sites so a caller can reproduce Python's `except WireError` scope with `is_wire_error()`; the vault port applies §3.5 to let the untagged case escape the same way Python's bare `ValueError` does |
| sshwire | `f"...{value!r}"` formats a `str` with CPython's `repr()`: single quotes unless the string contains `'` and not `"`, with `\n`/`\r`/`\t`/backslash/quote escapes and non-`str.isprintable()` characters as `\xNN`/`\uNNNN`/`\UNNNNNNNN` | `py_repr_str` reimplements the same algorithm; printability for the Unicode format (Cf) and private-use (Co) categories is approximated with explicit ranges rather than a full Unicode category table (unassigned/Cn codepoints are not checked at all, so they are always treated as printable) | No Unicode-category-table crate (e.g. one exposing `General_Category`) is present in the offline `cargo` registry cache this build uses (see the `pyjson`/`indexmap` row above for the same constraint), so `py_str_is_printable` hand-enumerates the Cf/Co ranges reachable in practice. This matches CPython exactly for every character reachable through this module's inputs (ASCII, C1 controls, common Unicode spaces/format controls, ordinary letters/symbols/emoji) and for everything the oracle tests in `src/sshwire.rs` exercise; only an obscure unassigned or exotic format/private-use codepoint outside those ranges could format differently |

| kms (`WrappedKey::from_dict` -> `python_str`/`python_repr`, finding B-2) | `str(value["key_id"])` on a JSON array or object recurses through Python's `repr()` for every nested element, using CPython's exact `unicode_repr` string-quoting/escaping rules and preserving `dict` insertion order | `python_repr` reproduces the same recursive `str`-of-container-is-`repr`-of-elements structure, but (1) object keys are emitted in sorted order, since this crate's `serde_json::Map` has no insertion-order feature available offline (same root cause as the existing `pyjson` "key order" row above), and (2) string escaping only covers the common cases (backslash, the chosen quote character, `\n`/`\r`/`\t`, and other C0 control bytes as `\xHH`), not CPython's full non-ASCII "is this codepoint printable" table | Per finding B-2, arrays/objects are explicitly allowed to be approximated or deviated from; scalars (`str`, `int`, `float`, `bool`, `None`) are matched exactly (see `oracle_key_id_coercion_matches_python` in `kms.rs`). This is unreachable through this crate's own `WrappedKey::to_dict`, which only ever emits `key_id` as a plain string; it can only be observed by feeding a hand-crafted JSON document (e.g. a corrupted or foreign-written vault file) with a non-scalar `key_id` field into `from_dict` |
| kms (`LocalFileKms::create`/`wrap`/`unwrap`, finding B-4) | A non-ASCII `key_id` makes `key_id.encode("ascii")` raise a bare, unwrapped `UnicodeEncodeError` -- not a `KmsError` or any `errors.py` class, so it is not `except ZeroPWError`-catchable. In `create` specifically, this happens *after* the parent directory (mode 0700) and the target file (0 bytes, via `os.open(..., O_CREAT \| O_EXCL)`) have already been created on disk, since the encode only happens once inside the final `stream.write(...)` call | `require_ascii_key_id` returns `KmsError("kms_key_id_not_ascii", key_id)`, fitting the same `Result<T, Error>` shape as every other failure in this module. In `create`, the check runs first, before any directory or file is created | `Result<T, Error>` has no equivalent of an arbitrary unwrapped exception escaping past the crate's own error type (same reasoning as the existing `kms`/TOCTOU row above). Checking first and writing nothing is a deliberate hardening over Python's actual behaviour (which leaves a stray empty file and an empty directory behind on this error path) rather than an attempt to match it; verified against real Python via `python3.12` during development (a non-ASCII `key_id` does leave a 0-byte file) |
| crypto/chacha20poly1305 (`encrypt`, finding B-5) | `encrypt` accepts a plaintext of exactly `_MAX_AEAD_MESSAGE = 0xFFFFFFFF * 64` bytes (~256 GiB): the pure-Python block loop has no additional internal limit beyond the explicit `len(plaintext) > _MAX_AEAD_MESSAGE` check | The `chacha20poly1305` crate's own internal counter bookkeeping refuses a message of exactly that length (one length short of this crate's own explicit `plaintext.len() as u64 > MAX_AEAD_MESSAGE` check, which is otherwise identical to Python's), so `encrypt` returns `SizeError` for that one boundary length where Python would succeed | Not exercised by any test (encrypting/decrypting an actual 256 GiB buffer is impractical) and not reachable in this system regardless: `zeropw/vault.py`'s `MAX_SECRET_BYTES = 64 * 1024` caps every value ever passed to `encrypt` at 64 KiB, twenty-two orders of magnitude below this boundary. Recorded per PORTING.md §3.1 (audited-crate substitution) rather than fixed, since fixing it would mean reimplementing the crate's internal block-counter accounting to avoid its off-by-one, for a length no caller can ever reach |

## Second-half seam

- `sshwire.rs` calls `ed25519_dalek` directly through a private `ed25519_adapter` module (marked `// ADAPTER: switch to crate::crypto::ed25519 after unit B merges`) instead of `crate::crypto::ed25519`, which is still a stub owned by a different work unit. The adapter exposes exactly the three operations `zeropw/sshwire.py`'s lazy `_ed25519()` import uses (`public_key_from_seed`, `sign`, `verify`) plus `generate_seed`, with verification strictness matched to `zeropw/crypto/ed25519.py` by hand (see the adapter's doc comments: it rejects non-canonical point encodings the way `_point_decode` does, since `ed25519_dalek`/`curve25519-dalek` are more lenient by default). This is not a behavioural deviation — the coordinator will rewire the call sites to `crate::crypto::ed25519` once it lands, with the same signatures.
